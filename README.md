# Jak funguje internet — Síť pod lupou

Česká síťová laboratoř pro badatelskou výuku. První etapa používá jednu společnou topologii: byt na Lipové, Matějovu domácnost, chatu se satelitním přístupem, propojené sítě poskytovatelů ve fiktivním městě Lipov, čtyři samostatná datová centra: hosting webu knihovny, DNS, pošty a chatbota, Instagram, hlavní cloud A a druhé cloudové centrum B, samostatné VPN centrum a mobilní síť se dvěma BTS. Zahrnuje také hackerské doupě, samostatný cizí hosting podvodného webu a kavárnu s notebookem hosta a napodobeným Wi-Fi hotspotem útočníka. Otázky a úkoly zadává učitel mimo aplikaci.

## Spuštění

Otevřete **index.html** v běžném současném prohlížeči. Funguje i přímo ze souboru, bez serveru, instalace, sestavení, databáze nebo API klíče. Všechny soubory z tohoto adresáře ponechte pohromadě. Aplikace nemá externí fonty, knihovny ani jiné síťové závislosti. Po úplném načtení aplikace probíhají všechny pokusy lokálně; modelové servery nevyžadují připojení k internetu.

Při každém novém otevření se vytvoří výchozí model. Obsah ani zásahy se neukládají do úložiště prohlížeče.

## Co lze vyzkoušet

- **Kavárna a MITM:** v mapě vyberte **Kavárna**, otevřete **Útočník v kavárně → MITM**, zapněte Napodobený hotspot a použijte Připojit hosta k napodobené Wi-Fi. Host začíná na běžné Wi-Fi; pouhé zapnutí hotspotu jeho provoz neodposlouchává. Obě nabídky se jmenují `Kavarna_hoste`, ve výukovém nastavení je rozlišuje jejich provozovatel. Po přepnutí vedou skutečné modelové pakety `notebook hosta → útočníkův hotspot → Wi-Fi kavárny → router s NAT → internet`. Útočníkův notebook zároveň představuje přenosový most se dvěma rádiovými rozhraními. Běžný notebook hosta má vlastní Prohlížeč, Poštu a Připojení; jeho stav se nemíchá s ostatními zařízeními.
- **Odposlech a změna HTTP:** v útočníkově aplikaci vyberte Pouze sledovat nebo Změnit HTTP stránku a Host načte HTTP. Krokujte či přehrajte přenos. Přehled ukládá jen pakety, které skutečně prošly útočníkem, s IP/porty pozorovanými na tomto místě. HTTP ukáže požadavek, vzkaz, Cookie a Set-Cookie. Při změně odpovědi se nadpis po cestě přepíše na „Tento obsah změnil útočník v kavárně.“ Host jej uvidí až po doručení; porovnejte nadpis na původním serveru, který zůstane beze změny. Záznam obsahuje obsah před a po změně. HTTP klient nemá automatický detektor podvržení; označení zásahu je pohled simulace u útočníka a v detailu paketu.
- **HTTPS v kavárně:** Host načte HTTPS otevře stejnou knihovnu. I přes útočníka dorazí původní obsah; HTTP metoda, vzkaz, cookies a odpověď zůstávají v jeho přehledu chráněné TLS. Běžný DNS a veřejná část ClientHello včetně SNI zůstávají viditelné. Volba Podstrčit certifikát připraví nedůvěryhodného TLS protějška: prohlížeč spojení odmítne před odesláním HTTP dat. Volba Poškodit HTTPS data změní jeden bajt chráněného požadavku; server odhalí chybu integrity a požadavek nezpracuje. Neexistuje tlačítko pro obejití ověření. Útočník v tomto modelu nedokáže vytvořit platnou změněnou HTTPS odpověď.
- **Obrana a výpadky v kavárně:** na notebooku hosta v Připojení zvolte Wi-Fi kavárny; další přenos útočníka obejde. Zapněte VPN: i HTTP a DNS jsou při průchodu kavárnou uvnitř chráněného VPN obalu. To nešifruje HTTP za výstupem VPN, ale tento útočník se nachází před ním. Vypnutí hotspotu, notebooku útočníka či jeho spoje přeruší vybranou cestu a samo hosta nepřepne na jinou Wi-Fi. Při změně připojení během přenosu původní pokus skončí; nové načtení použije aktuální cestu. Záznamy jsou nejvýše 20 posledních paketů a lze je vymazat. Ostatní domácnosti zůstávají nezávislé.

- **Phishing v hackerském doupěti:** přepněte mapu na **Doupě**, klikněte na Počítač útočníka a otevřete **Phishing**. Vyberte některý ze čtyř notebooků nebo telefon a odešlete připravený e-mail. Krokování či přehrání jej přenese přes vlastní router s NAT k poštovnímu serveru v hostingu. E-mail se tam uloží i při vypnutém příjemci; potvrzení se vrátí zvlášť. Otevřete Poštu u příjemce a použijte **Zkontrolovat poštu**. Zpráva se zobrazí až po doručení odpovědi ze schránky. Stejnou Poštu má všech pět běžných zařízení.
- **Falešná knihovna a HTTPS:** otevřený e-mail ukáže jméno i úplnou adresu odesílatele, text odkazu a skutečný cíl `https://knihovna-podpora.test/overeni?zprava=…`. Kliknutí spustí DNS, modelový TLS a načtení z jiného serveru `192.0.2.170`. Má vlastní platný certifikát pro svou doménu; HTTPS šifruje přenos k tomuto serveru, neověřuje poctivost stránky. Pouhé otevření stránky v pokusu přihlášení neodesílá. Formulář obsahuje jen pevné, neupravitelné fiktivní údaje `ctenar-demo` / `UKAZKOVE-HESLO`. Odeslat ukázkové přihlášení vyvolá nový POST; údaje se uloží až na podvodném serveru po přijetí a dešifrování. Na počítači útočníka použijte **Načíst záznamy ze serveru**: kopie se zobrazí až po samostatném síťovém přenosu. Přepínačem HTTP lze porovnat čitelnost stejného formuláře. Cookie pravé `knihovna.test` se jiné doméně neposílá.
- **Rozpoznání a obrana:** v Poště použijte **Označit jako phishing · zablokovat odkaz**, nebo otevřete známou adresu knihovny. Označení je místní stav zařízení; blokuje odkaz i odeslání formuláře příslušného pokusu, nemaže již přijaté údaje na serveru a neodesílá hlášení externí službě. Nový e-mail je samostatný pokus. Poštovní server i Podvodný web mají informační okna nad mapou. Správcovský přehled ukazuje skutečný stav serveru, zatímco útočníkův počítač jen naposledy přijatou kopii. Lze odpojit přípojky či vypnout servery, použít Wi-Fi, mobilní data, satelit i VPN. Při výpadku zůstávají již uložené zprávy a údaje na serveru; opakování stejného přenosu po ztrátě potvrzení je nezdvojí.

- **Cookies a rozpoznání prohlížeče:** na kterémkoli běžném zařízení otevřete Prohlížeč a načtěte knihovnu přes HTTP. První požadavek cookie nemá. Server vytvoří záznam v1 a do odpovědi vloží `Set-Cookie: navstevnik=v1; Path=/; Max-Age=3600; HttpOnly; SameSite=Lax`. Prohlížeč cookie uloží až po skutečném doručení odpovědi. Při dalším načtení odešle `Cookie: navstevnik=v1`; stránka ukáže Vítej zpět, stejné ID a počet načtení 2. Cookies cestují v hlavičkách webových požadavků a odpovědí, nikoli samostatným zvláštním paketem. HTTP značky mají popisek Cookie / Set-Cookie a v detailu zvýrazněnou hlavičku.
- **Úložiště a záznamy serveru:** tlačítko Cookies v prohlížeči otevře jeho vlastní úložiště s hodnotou, webem, cestou, platností a příznaky, posledními odeslanými/přijatými hlavičkami a vysvětlením rozhodnutí. Přes odkaz otevřete okno webového serveru: obsahuje tabulku ID, počty načtení, všechny požadavky a poslední pozorovanou IP. Zvýrazní se skutečně použitý záznam. Smazat cookies odstraní jen místní cookie; starý serverový záznam zůstane a další načtení dostane nové ID. Přepínač Povolit cookies pro tento web zastaví přijímání i odesílání, ale dříve uložené položky zachová do smazání či vypršení. Web funguje dál a každý požadavek bez platného ID vytváří nový záznam. Zobrazená stránka zůstává snímkem poslední odpovědi; smazání cookies samo nenačte novou stránku.
- **Cookies mezi zařízeními, přes VPN a HTTPS:** každý notebook i telefon má vlastní prohlížeč, DNS, cookies a stránku. Dvě zařízení na stejné Wi-Fi dostanou různá ID, přestože sdílejí veřejnou IP přes NAT. Změna kabel/Wi-Fi/data ani přepnutí VPN uloženou cookie neodstraní; server může podle stejného ID rozpoznat prohlížeč i na jiné veřejné IP. V HTTP jsou Cookie/Set-Cookie čitelné, TLS je chrání společně s dalším HTTP obsahem. Za HTTP uvnitř VPN jsou čitelné až po odstranění VPN obalu; HTTPS zůstává chráněné i za výstupem VPN. V okně serveru zapněte Vyžadovat HTTPS pro cookie · Secure a dokončete načtení přes HTTPS. Teprve doručená odpověď změní uložený příznak. Potom HTTP požadavek cookie neodešle; `Set-Cookie` se Secure přijatou přes HTTP prohlížeč odmítne a HTTP nepřepíše dřívější Secure cookie. HTTPS ji dál používá.
- **Vypršení cookies:** Posunout čas o 1 hodinu posune společný modelový čas cookies všech zařízení. Cookie platí hodinu od poslední doručené odpovědi. Po uplynutí se odstraní z prohlížeče a další načtení přidělí nové ID; serverové záznamy zůstanou. Tyto hodiny jsou samostatná výuková pomůcka pro cookies, ne reálný čas ani rychlost přenosu. Ovládání změn cookies je během přenosu neaktivní.

- **Chata a satelitní internet:** přepínač mapy Satelit ukáže notebook na chatě, domácí switch, Wi-Fi Chata, router, venkovní anténu, satelit LEO a pozemní stanici. Notebook začíná na Wi-Fi; v Připojení lze vybrat i kabel. Wi-Fi/kabel je místní přístup k routeru, satelit je jeho přípojka k poskytovateli. Otevřete Prohlížeč: DNS i HTTP/HTTPS jdou `notebook → AP/switch → router s NAT → anténa → satelit → pozemní stanice → B → hosting`, odpovědi zpět. Stejnou skutečnou trasu modelu používá Instagram, cloud i chatbot; funguje také VPN. Obrázek ukáže více skupin paketů současně na obou rádiových úsecích. Notebook má vlastní prohlížeč, rozepsané texty, historii chatbota a místní cloudové soubory; cloud používá stejný účet Ty jako notebook na Lipové. Tiskárna na chatě není, proto zde není aplikace Dokument.
- **Výpadek satelitní cesty:** v okně antény použijte Zakrýt výhled antény. Místní Wi-Fi zůstane připojená, ale další internetový přenos selže. Obnovte výhled a opakujte akci. V okně routeru lze odpojit jeho satelitní přípojku; jednotlivě lze vypnout anténu, satelit i pozemní stanici nebo přerušit jejich spoje. Ostatní domácnosti mají své nezávislé pozemní připojení. Na notebooku jsou odkazy do detailu routeru a antény. Všechny nové detaily se otevírají nad mapou; detail paketu dál zastavuje animaci.

- **Kabel a Wi-Fi:** v notebooku otevřete aplikaci Připojení nebo ikonu sítě vpravo na hlavním panelu. Vyberte Kabel, Wi-Fi nebo Odpojit. V bytě je připravená síť `Lipova`, u Matěje `U Mateje`. Přenos přes Wi-Fi jde rádiem do přístupového bodu, potom kabelem do switche. Oba notebooky mohou používat Wi-Fi. Zkuste vypnout AP: kabel zůstane použitelný. Místní tisk přes Wi-Fi funguje i bez domácího routeru, pokud zůstávají zapnuté AP, switch a tiskárna.
- **Telefon a mobilní data:** v bytě na Lipové je Tvůj telefon. Po kliknutí otevře vlastní obrazovku s Poštou, Prohlížečem, Instagramem, Chatbotem a Připojením. Vyberte Wi-Fi nebo Mobilní data; telefon začíná na datech přes BTS Lipová. Lze také zvolit BTS Park. Přenos vede `telefon → BTS → síť operátora → router C → internet`, odpověď zpět. Vypněte domácí router: data dál fungují, domácí Wi-Fi ztratí cestu ven. Vypněte vybranou BTS nebo její přípojku a vyberte druhou věž. Pohled Mobilní síť ukáže obě BTS a uzel operátora.

- **Chatbot a výpočet na serveru:** na ploše notebooku doma, u Matěje, na chatě nebo telefonu otevřete Chatbot a napište libovolný dotaz. Odeslat dotaz připraví skutečné modelové pakety k serveru `203.0.113.30` v hostingu. Krokujte nebo přehrajte přenos: celý dotaz nejprve dorazí na server, následují tři kroky zpracování a potom cesta odpovědi zpět. Odpověď je pro každý dotaz stejná a zařízení ji zobrazí až po přijetí všech bajtů. Přes šipku v aplikaci otevřete server: uvidíte přijatý dotaz, průběh zpracování a počet dokončených výpočtů. Při zpracování se server zvýrazní v mapě. Vypněte jej během výpočtu nebo přerušte návratovou cestu: odpověď se v zařízení neobjeví. Znovu zapněte server a opakujte pokus. Každé zařízení má vlastní historii konverzace i rozepsaný dotaz.

- **Cloud a soubory:** v obou noteboocích otevřete aplikaci Cloud. Na kartě V počítači je textový soubor; lze ho upravit, uložit místně nebo vytvořit nový. Uložit na cloud odešle soubor na cloudový server v datovém centru. Na kartě Na cloudu použijte Obnovit seznam; soubor stáhnete tlačítkem Stáhnout kopii. Stažený text je nová místní kopie a sám se nesynchronizuje. U souboru, který vlastníte, nastavíte přístup pro druhého uživatele: soukromý, čtení/stažení nebo také úpravy. Změnu odešlete tlačítkem Uložit přístup a dokončete přenos krokováním nebo přehráním. S právem upravovat lze stáhnout soubor, změnit místní text a použít Uložit novou verzi; vlastník a ID původního cloudového souboru se zachovají. Nahrát jako nový soubor vytvoří vlastní soukromou kopii. Předpřipravený Plán na víkend.txt vlastní Matěj a tobě ho sdílí ke čtení. Vyzkoušejte odebrání přístupu a pokus stáhnout soubor podle známého ID. Samotná znalost ID přístup neuděluje.

- **Čtyři datová centra:** přepínač Centra ukáže hosting, Instagram, cloud A a cloud B. Každé má vlastní router, switch, podsíť a přípojku. Vypněte přípojku hostingu: web a DNS přestanou být dostupné, ale Instagram a cloud dál fungují. Okna zařízení vysvětlují, ke kterému centru patří.
- **Kopie v druhém centru:** nahrajte soubor do cloudu A. Přes šipku v aplikaci otevřete jeho server a použijte Synchronizovat centra A → B. Soubory i práva vyrazí jako samostatné pakety do druhé budovy. Po dokončení v aplikaci Cloud vyberte B · kopie ke čtení, obnovte seznam a stáhněte soubor. Funguje i při vypnutém serveru A nebo jeho přípojce. B je jen ke čtení; změny ukládejte do A a potom znovu synchronizujte.
- **VPN a paket uvnitř paketu:** v aplikaci Připojení zapněte přepínač VPN. Je nezávislý na kabelu, Wi-Fi i mobilních datech a funguje v obou noteboocích i telefonu. Internetový provoz včetně DNS se zabalí do neprůhledného IPv4/UDP obalu s cílem VPN server `192.0.2.130`. V mapě má podobu většího fialového paketu se skrytým vnitřním paketem; postupně se zvýrazní skutečně projeté úseky tunelu. Nový přepínač mapy VPN ukáže jeho samostatné centrum. Na VPN serveru se obal ověří a odstraní, vnitřní paket pokračuje běžnými spoji ke službě a zdrojová IP se přeloží na veřejnou IP VPN serveru. Odpověď se vrací podle jeho tabulky, znovu se zabalí a rozbalí až v zařízení. Detail vnějšího paketu ukáže čitelné IP/UDP údaje a chráněný vnitřek; po rozbalení je dostupný původní paket a historie obalu. Otevření detailu zastaví animaci stejně jako u ostatních paketů.
- **HTTP, HTTPS a VPN:** pošlete stejný vzkaz knihovně přes HTTP bez VPN, HTTP s VPN a HTTPS s VPN. HTTP je v tunelu skryté, po výstupu z VPN opět čitelné. HTTPS má uvnitř VPN svou další ochranu TLS a po odstranění VPN obalu zůstane neprůhledné až k webovému serveru/prohlížeči. V okně webového serveru se ukazuje skutečná zdrojová IP a port požadavku; se zapnutou VPN to je IP VPN serveru. Okno VPN serveru ukazuje tunely klientů, čitelný HTTP obsah nebo stále chráněné HTTPS a samostatný výstupní NAT/PAT. Vypněte VPN server: přenos selže a sám se nepřepne na přímou cestu. Místní tisk VPN obchází a funguje i při výpadku VPN. Zapnutí/vypnutí VPN nebo změna přístupu ukončí nedokončený přenos; další pokus použije aktuální nastavení. DNS cache se při přepnutí VPN vyprázdní, aby šla sledovat i cesta DNS.

- **HTTP a HTTPS:** na notebooku nebo telefonu otevřete Prohlížeč. Tlačítka HTTP / HTTPS otevřou stejnou knihovnu na `http://knihovna.test` a `https://knihovna.test`. Oba přístupy používají stejný server a DNS; HTTPS navíc názorně naváže TLS a ověří certifikát před odesláním požadavku. Na stránce napište Vzkaz knihovně (do 160 znaků) a odešlete jej. U HTTP je v detailu paketu čitelná metoda, cesta i text; u HTTPS se zobrazí chráněný modelový záznam, zatímco IP adresy a porty zůstávají viditelné. Sledovat v mapě skryje monitor; Krok/Přehrát projde přenosem, ověřením, šifrováním a dešifrováním na koncích. Server zpracuje formulář až po přijetí a případném dešifrování. Potvrzení se v zařízení objeví až po doručení odpovědi. Detail serveru ukazuje čitelný poslední požadavek a modelový stav certifikátu: zkuste prošlou platnost, jinou doménu nebo nedůvěryhodného vydavatele. Nové HTTPS spojení selže před odesláním formuláře; HTTP certifikát nepoužívá. Platný certifikát obnovte před dalším HTTPS pokusem. Všechna data zůstávají lokálně v simulaci.
- **Změna webu:** na webovém serveru změňte nadpis. Už otevřená stránka se nezmění; nový HTTP i HTTPS požadavek doručí aktuální obsah.
- **Místní tisk:** na ploše notebooku otevřete Dokument a odešlete ho do tiskárny. V detailu Přípojky bytu odpojte spoj a zkuste tisk i vzdálený web. Pro tisk nepotřebujete ani zapnutý domácí router, pokud notebook, switch a tiskárna zůstávají připojené.
- **Text, obrázek a video:** v Instagramu vyberte typ obsahu. Text se počítá podle skutečných UTF-8 bajtů rozepsané zprávy (výchozí 363 B = 1 datový paket). Obrázek má modelově 100 kB = 72 paketů, video 5 MB = 3 572 paketů. Všechny tři varianty používají nejvýše 1 400 B dat na paket. Počet určuje velikost, nikoli přípona souboru. Před odesláním uvidíte náhled a rozdělení, při přenosu samostatná počítadla odeslání a přijetí na obou spojeních. Na mapě se menší přenosy zobrazují po paketech, obrázek po skupinách nejvýše 10, video po nejvýše 100. Klikněte na skupinu, rozbalte ji a prozkoumejte jednotlivý paket. U Matěje se obsah zobrazí až po úplném složení; doručené ukázkové video má přehrávač.
- **Instagram:** na ploše notebooku nebo telefonu otevřete Instagram a pošlete zprávu účtu `@matej`. První spojení doručí data na Instagram, který zprávu uchová. Pak vzniknou nové pakety pro druhé spojení do Matějovy domácnosti. Vypněte Matějův notebook nebo odpojte jeho přípojku: zpráva počká na Instagramu. Po obnovení připojení se připraví doručení; spusťte ho krokováním nebo přehráním. U Matěje otevřete Instagram. Potvrzení přečtení se vrátí přes server do zařízení, ze kterého byla zpráva odeslána. Před otevřením zprávy ho můžete vypnout přepínačem na Matějově ploše. Detaily paketů ukazují adresy, samostatná spojení i různé TCP SEQ.
- **NAT a sdílená veřejná adresa:** načtěte web nebo odešlete zprávu a krokujte až k domácímu routeru. Jeho okno ukazuje tabulku NAT/PAT: soukromou IP a port zařízení, veřejnou IP a přeložený port, protějšek a počty paketů v obou směrech. Detail paketu ukáže hlavičku před a po překladu. Notebook a telefon na stejné Wi-Fi sdílejí veřejnou adresu, ale dostanou odlišné překlady. Prohlédnout NAT routeru lze také z aplikace Připojení. Zkuste tabulku vymazat po odeslání webového požadavku: vracející se odpověď už nelze přiřadit. Nový pokus vytvoří nový záznam. Místní tisk NAT nepoužívá.
- **Náhradní cesta:** v celkové mapě načtěte web, odpojte používaný spoj horní větve A–B–D a zopakujte načtení. Přenos projde dolní větví A–C–D. Odpojte i tu: přenos selže. Přípojka hostingu odpojí jen web a DNS; další centra mají vlastní přípojky.

Akce začne **pozastavená**. Přehrát zapne animaci, Pauza zastaví všechny pohybující se pakety. Krok posune společný časový krok sítě: na různých spojích může současně proběhnout více událostí. Části zprávy odcházejí s odstupem a další vyrazí ještě před doručením předchozí. Čísla na paketech pomáhají sledovat jednotlivé části. Pakety projíždějí přes středy zařízení; při rozhodování zůstávají na uzlu a další úsek začíná na stejném místě. Trasa se nezkracuje před kolečkem a paket neodskočí nad zařízení. Přehrávání používá stálé tempo; interval animace není měřením rychlosti sítě. Opakovat stejnou akci lze i v průběhu pokusu: ukončí aktuální přenos, připraví znovu stejný obsah a zachová zapojení, napájení, naučené MAC adresy, DNS cache, tabulky NAT i uložený obsah serveru. Pokud už zprávu převzal Instagram a čeká její doručení, opakování obnoví druhou fázi z uchovaného textu. Úplný výchozí stav vrátíte novým načtením aplikace v prohlížeči.

### Co se skutečně modeluje

- **Cookies jsou stav prohlížeče a identifikátor pro server.** Každé z pěti běžných klientských zařízení má oddělené úložiště cookie prvé strany `navstevnik` pro `knihovna.test`, host-only a cestu `/`. Výběr respektuje web, cestu, povolení, Secure a modelovou platnost. Do požadavku se posílá jen název a hodnota, nikoli atributy Max-Age, HttpOnly nebo SameSite. Server vyhledává pouze doručené ID ve své mapě, bez přiřazování podle IP nebo názvu zařízení; neznámé či chybějící ID vytvoří nový záznam. GET zvýší počet načtení stránky, GET i POST počet všech požadavků. Přijatá odpověď obsahuje samostatný snímek ID/počtů a původního obsahu; při chybě nepřepíše starou stránku. Hlavička Set-Cookie se zpracuje až u klienta po doručení a případném ověření/dešifrování TLS. Při ztrátě odpovědi proto může na serveru vzniknout záznam, který se v klientovi nikdy neuloží. Přenosové hlavičky, počty a rozhodnutí v oknech vycházejí z téhož modelového stavu.

- **Satelitní přístup propojuje domácí WAN s pozemní bránou.** Soukromá LAN chaty `192.168.30.0/24` se neinzeruje poskytovatelům. NAT na routeru používá veřejnou modelovou WAN `192.0.2.53`; koncem přenosové části v pozemní stanici je `192.0.2.54`. Stanice má samostatnou přípojku do B v `192.0.2.56/30`. Routery směrují a snižují TTL, anténa a satelit předávají v tomto modelu původní IP paket bez změny jeho hlaviček či TTL. Přenosová část je abstraktní obousměrný kanál, ne ethernetová LAN mezi Zemí a vesmírem; detail neukazuje její interní MAC. Každý rádiový úsek má dvě průběžné události letu a třetí událost příchodu. Animace navazuje po třetinách stejné spojnice a přes středy ikon, další pakety mohou být současně na cestě. Při přerušení během letu se paket ztratí. Události mají modelový čas, nikoli skutečné milisekundy. HTTPS a VPN zůstávají samostatnými vrstvami; satelit sám aplikační obsah nezabezpečuje.

- **VPN je další vrstva, nikoli jiný fyzický přístup.** Notebook a telefon dál používají stejné přístupové spoje a fyzické IP; virtuální adresy tunelu jsou `10.8.0.10` (notebook), `.11` (Matěj), `.12` (telefon), `.13` (chata), `.14` (počítač útočníka v doupěti) a `.15` (host v kavárně). Modelový vnější protokol je UDP/51820. Původní IP/TCP nebo IP/UDP paket je oddělený od neprůhledného obalu. Směrování a domácí NAT pracují s vnějšími poli; VPN server používá pozorovanou veřejnou adresu a port klienta pro návrat. Výstupní NAT VPN serveru samostatně přiřazuje klienty a protějšky, takže se ani stejné zdrojové porty dvou klientů nesmíchají. Po rozbalení se obnoví vnitřní TTL a VPN server jej při předání sníží; routování vnějšího obalu neodečítá TTL vnitřního paketu. Vrstva HTTPS/TLS zůstává uvnitř VPN zachovaná. Klíče a protějšky jsou v této etapě připravené.

- **Wi-Fi je součást domácí LAN.** AP přemosťuje rámce mezi rádiem a Ethernetem, učí se MAC a přeposílá podle stejného principu jako switch. Jeho logické porty `wifi1`/`wifi2` představují připojené klienty. Samostatné AP mají kabel do příslušného domácího switche. Nepřidávají směrovací skok ani nesnižují TTL. Rozeslané kopie mají vlastní větvení; kopie přes AP nepřesouvá hlavní paket a její zahození nezruší platnou cestu.
- **Mobilní přístup vede přes BTS a operátora.** BTS předává uživatelská data mezi rádiovým úsekem a přípojkou do mobilního jádra. Vnitřní IP paket na BTS nemění koncové adresy ani TTL. Uzel Síť operátora shrnuje uživatelskou část jádra a bránu do internetu (například UPF); teprve tento uzel směruje do internetu a snižuje TTL. Logický prefix `198.51.100.0/24` a rozhraní `mobile1`/`mobile2` představují mobilní kanál, nikoli ethernetovou LAN mezi telefonem a věží. Připravená vratná cesta vede přes zvolenou BTS. Ethernetové MAC se na této části nezobrazují.
- **Zařízení používá jeden vybraný přístup.** Notebooky mají kabel/Wi-Fi, telefon Wi-Fi/data a obě varianty nabízejí odpojení. Pevné adresní profily přidělí každému přístupu jeho IP; Wi-Fi má jinou MAC i IP než kabel. Přepnutí aktivního spojení přeruší jeho nedokončený přenos a pro nové připojení je nutný nový pokus. Už přijatá zpráva na Instagramu zůstává uchovaná. Pozdější potvrzení přečtení se může vrátit na nové připojení původního zařízení.
- **Telefon má vlastní prohlížeč a DNS cache.** Stránka v notebooku a v telefonu jsou samostatné. Instagram na obou zdrojových zařízeních představuje stejný účet a jeden poslední chat; rozepsané texty jsou oddělené. Potvrzení se vrací konkrétnímu zařízení, které odeslalo zprávu.

- **Switch se učí zdrojovou MAC a vstupní port z příchozího rámce.** Cílovou adresu ze stejného rámce se nenaučí. Počáteční MAC tabulky jsou prázdné. Neznámý unicast pošle na ostatní aktivní přeposílající porty své LAN, známý pouze na odpovídající port. Neurčená kopie je na jiném koncovém zařízení zahozena, aniž by se změnila její cílová MAC. Nejde o broadcastový rámec. Odpojené porty se z naučené tabulky odstraní; vypnutí switche vyprázdní jeho tabulku.
- **Router hledá nejpřesnější prefix pro cílovou IP** ve své aktuální tabulce. Ukáže použitý záznam, rozhraní a IP dalšího routeru. Přepisuje ethernetový obal a snižuje TTL. Běžné směrování zachovává koncové IP adresy; domácí router navíc na hranici LAN/WAN provádí NAT. Soukromý prefix domácnosti je pouze v tabulce jejího routeru. Poskytovatelé směrují k veřejné WAN adrese domácnosti a znají také veřejné cílové sítě a přímo připojené sítě /30.
- **NAT/PAT překládá adresu i port.** Při cestě z domácnosti do internetu router uloží protokol, soukromou IP a port, přidělený veřejný port a vzdálenou IP a port. Více zařízení tak sdílí jednu veřejnou adresu. Příchozí odpověď musí odpovídat tomuto záznamu včetně protějšku; před směrováním do LAN se obnoví její cílová IP a port. Bez záznamu se příchozí paket zahodí s vysvětlením. Datový obsah a TCP SEQ se překladem nemění; směrování dál sníží TTL jednou na router. Všechny tři domácí routery překládají TCP i UDP, pro kabel i Wi-Fi; router doupěte má vlastní NAT pro kabelový počítač a kavárna samostatný NAT pro hosta. Záznamy se zachovají mezi pokusy, odstraní se při vypnutí routeru, výpadku jeho LAN/WAN, změně připojení příslušného zařízení nebo ručně tlačítkem.
- **Cesta je stabilní.** Počet propojení modelové cesty je jednotná metrika; satelitní cesta zahrnuje i přenosové uzly antény a satelitu. Při rovnocenných cestách je deterministicky vybrána horní větev; model nepoužívá náhodné rozdělování paketů mezi cesty. Po změně dostupnosti se konzistentní tabulky odvodí ihned, bez simulace konvergence konkrétního směrovacího protokolu. Geometrie ani zeměpisná vzdálenost nejsou metrikou.
- **Předání je diskrétní událost.** Události mají společné logické časové kroky; všechny události stejného kroku se přehrají současně. Zařízení zahajuje další paket nebo zobrazovanou skupinu po třech těchto krocích. Každý spoj předá v jednom směru v jednom kroku nejvýše jeden rámec nebo jednu zhuštěnou skupinu, zatímco různé spoje i opačné směry mohou pracovat současně. Běžná událost pohybu znamená příchod na další uzel; satelitní rádio má navíc dvě průběžné události letu před příchodem. U ostatních spojů animace tuto už provedenou událost přehrává. Následující krok zpracuje rámec či rozhodnutí routeru. Odpojení po dokončeném příchodu již přijatý rámec nezruší. Pokud se spoj přeruší po výběru výstupu a před dalším předáním, tento paket se ztratí; nepřemístí se na alternativní spoj. Nový pokus použije aktuální tabulky. Při chybě se celý pokus zastaví včetně ostatních čekajících a cestujících částí.
- **DNS a web jsou dva různé servery.** DNS používá UDP/53, web HTTP přes TCP/80 nebo modelový HTTPS přes TLS nad TCP/443. Notebook má adresu DNS serveru připravenou a úspěšný záznam A si pamatuje do obnovení modelu. Modelový prohlížeč přijímá `knihovna.test`, `knihovna.test/`, `http://knihovna.test/` a `https://knihovna.test/`; nevytváří skutečné požadavky na tyto adresy.
- **HTTPS chrání HTTP obsah, nikoliv směrovací informace.** Modelový TLS handshake používá ClientHello, společný serverový přenos ServerHello a chráněného certifikátu, ověření certifikátu a klientské dokončení. Teprve potom vznikne šifrovaný aplikační požadavek. Jeho dešifrování a zpracování na serveru, šifrování odpovědi a dešifrování v prohlížeči jsou samostatné události. Uvnitř paketů jsou jen neprůhledné modelové záznamy; původní obsah uchovává oddělený model koncových bodů. Kontrola porovnává doručené chráněné bajty s vytvořeným záznamem a při změně odmítne data. Jde o názorný princip důvěrnosti a integrity, ne skutečnou kryptografii. IP a TCP pole zůstávají dostupná směrování a NAT. DNS a ClientHello/SNI v tomto modelu zůstávají čitelné. HTTPS nepotvrzuje pravdivost webu.
- **Web má `Cache-Control: no-store`.** Každé načtení/obnovení musí projít sítí. Předchozí vykreslený dokument přitom zůstává na obrazovce do úspěšné nové odpovědi. Při chybě je výslovně označen jako dřívější obsah. Server zkopíruje text do odpovědi při přijetí HTTP požadavku, ne při začátku animace ani při doručení odpovědi.
- **Chatbot odděluje odeslání, výpočet a zobrazení.** Text dotazu a odpovědi se přenáší v UTF-8 segmentech do 1 400 B, s odstupem. Až po přijetí celého dotazu server provede tři samostatné modelové kroky a vytvoří pevnou odpověď. Klient ji neuvidí, dokud se nesloží celá odpověď. Pro odpověď server použije pozorovanou IP a port přijatého požadavku, takže funguje domácí NAT i mobilní data. Při opakování se založí nový pokus; předchozí chybné dotazy a již doručené odpovědi zůstanou v historii.
- **Cloud skutečně přijímá požadavek a posílá odpověď po modelové síti.** Upload, seznam, stažení i změna práv používají samostatný pokus přes TCP/443. JSON požadavek a odpověď se dělí na části do 160 B, odcházející s odstupem. Server provede změnu až po přijetí všech bajtů požadavku. Notebook přijme seznam, potvrzení nebo novou místní kopii až po složení celé odpovědi. Bajty zahrnují i aplikační metadata, proto velikost přenosu převyšuje velikost samotného textu.
- **Cloud má dvě fyzicky oddělené modelové lokality.** A obsluhuje čtení i zápis. B uchovává samostatnou kopii mapy souborů včetně vlastníků, verzí a práv a obsluhuje seznam/stažení. Synchronizace A → B je samostatná akce: celý snímek se segmentuje a skutečně přenese po síti. Až po přijetí všech bajtů se atomicky nahradí stará kopie. Výpadek přenosu zachová předchozí úplnou kopii. Při nové změně v A se B označí jako neaktuální a čtení odmítne odpovědí 503, aby stará práva neobešla odebrání přístupu. Po synchronizaci platí aktuální oprávnění; nepovolený zápis do B vrací 405. Výchozí kopie sdíleného souboru je připravená.
- **Práva kontroluje cloudový server.** Účty Ty a Matěj mají připravené přihlášení; IP adresa neurčuje oprávnění. Nový soubor je soukromý. Vlastník může druhému účtu povolit čtení a stažení nebo i úpravy; sdílení smí měnit jen vlastník. Soukromý soubor není v cizím seznamu a známé ID kontrolu neobejde. Zamítnutí 403, neexistující soubor 404 a konflikt verze 409 jsou doručené aplikační odpovědi, nikoliv ztracené pakety. Starý seznam je snímek poslední odpovědi; po změně přístupu je potřeba ho obnovit. Odebrání přístupu nemůže smazat už staženou místní kopii ani vzít zpět odpověď, kterou server už odeslal.
- **Cloudová verze a místní kopie jsou různé věci.** Místní editor funguje i bez sítě. Uložení nové verze kontroluje oprávnění a výchozí verzi kopie; starší kopie nepřepíše novější obsah na serveru. Přerušený upload původní obsah nezmění. Pokud byl požadavek proveden a ztratí se až odpověď, server změnu uchová; opakování stejné operace s jejím ID nezaloží duplicitní soubor ani nezvýší verzi podruhé. Cloudový server nabízí nad mapou označený správcovský přehled globálního stavu.
- **Instagram propojuje dvě samostatná spojení.** V prvním se do služby přenese celý obsah; teprve po jeho přijetí server připraví doručení. Kabelový notebook odešle paket z `192.168.10.10`, v internetu už má zdroj `192.0.2.1` a přeložený port. Matějův notebook nejprve odešle modelový paket Připojení směrem k Instagramu, aby vznikl jeho vlastní záznam NAT. Server si zapamatuje pozorovanou veřejnou adresu a port, na které pak pošle zprávu; Matějův router obnoví cíl `172.16.20.10:52002`. Soukromou adresu server v internetu neoslovuje. Platný kanál se při dalším přenosu použije znovu; po jeho ztrátě je nutné nové odchozí připojení. Stejný princip platí pro návrat potvrzení přečtení. Pro Wi-Fi a telefon se použije aktuální přístup. Oba směry mají vlastní pakety a TCP číslování: od tebe SEQ 1001, od Instagramu k Matějovi SEQ 8001. Příjemce je v aplikaci určen účtem `@matej`.
- **TCP dělí bajty na každém spojení samostatně.** Pro srovnání obsahu používají obě spojení Instagramu nejvýše 1 400 B dat v jednom segmentu. Výchozí zpráva 363 B vytvoří jeden datový paket na každém spojení; delší text se skutečně rozdělí. Obrázek 100 000 B vytvoří 72 a video 5 000 000 B celkem 3 572 datových paketů na každém spojení. Od Instagramu vznikají nové identity a TCP číslování, i když při stejné velikosti segmentu zůstává počet stejný. Příjemci skládají přesné bajty podle pozice a text se dekóduje až po složení všech dat. Jednotlivé IP pakety mají nejvýše 1 440 B (20 B IPv4 + 20 B TCP + data); nejde o fragmentaci IP. Údaje pořadí a skupin jsou školní pomůcky oddělené od polí protokolu. TCP samo hranice zpráv nezná; délku řeší modelová aplikace.
- **Skupina je zhuštěné zobrazení více paketů.** Do 16 datových paketů se zobrazují jednotlivě, do 200 po skupinách nejvýše 10, větší přenosy po nejvýše 100. Poslední skupina může být kratší. Všech 5 MB modelových bajtů se uchová a přesně znovu složí, ale směrovací a animační události se zpracují za celou skupinu společně. Skupina není velký paket na vodiči. Detail nejprve vysvětlí rozsah; Rozbalit skupinu nabídne jednotlivé pakety s vlastním SEQ, bajty a délkou do MTU. Mají společnou modelovou polohu, trasu, NAT a stav doručení. NAT počítá všechny datové pakety ve skupině, ne pouze značky. Samostatné řídicí připojení a potvrzení přečtení jsou další pakety a nepatří do uvedených datových součtů.
- **Převzetí, doručení a přečtení jsou různé stavy.** Přijatý text zůstává na Instagramu i při nedostupném příjemci. Odpojení odesílatele po převzetí nebrání pozdějšímu doručení Matějovi. Při výpadku druhé fáze server uchová zprávu a nový pokus vytvoří nové pakety; nejde o simulaci TCP retransmise. U Matěje se zpráva přečte po otevření jeho konverzace. Se zapnutými potvrzeními jde oznámení nejprve `Matěj → Instagram`, potom `Instagram → ty`. Teprve po přijetí druhé části ukáže tvůj Instagram Přečteno. Potvrzení může rovněž počkat na obnovení připojení. TCP ACK se s potvrzením přečtení nezaměňuje.

### Co první etapa skrývá nebo předpokládá

- MITM v kavárně je místní výukový scénář napodobeného hotspotu (evil twin). Host si vybere připravenou cestu; nevykonává se skutečné vysílání Wi-Fi, deautentizace, ARP spoofing, DHCP, získání hesel Wi-Fi, kompromitace zařízení ani konfigurace systémové sítě. Dva modelové spoje hosta představují volbu přístupového bodu pro jediné připojení. Notebook útočníka je zároveň zjednodušený přemosťující hotspot. HTTP změna přepisuje pouze pevný modelový nadpis; úplný TCP proxy, přečíslování segmentů a kontrolní součty se nesimulují. Nabídnutí vlastního certifikátu je připravená modelová větev TLS handshake s nedůvěryhodným vydavatelem, nikoli kryptografické prolomení nebo kompletní dvojice TLS relací. Poškození záznamu naopak prochází stávající kontrolou integrity modelu. Útočník nikdy neotevírá TLS/VPN aplikační záznamy; jeho přehled nevypisuje jejich vnitřní obsah. HTTPS a VPN nebrání přerušení dostupnosti cesty. Přehled může ukazovat starší pokusy s jiným nastavením; každý řádek uvádí ID paketu/pokusu a stav platný při jeho zachycení.

- Phishing je uzavřený výukový scénář s pevnou zprávou, adresami `.test`, připravenými účty a pouze dvěma modelovými weby. Neupravuje skutečné e-maily, nezískává skutečná hesla ani nevolá síťové služby. Pošta má jednu poslední zprávu v každé z pěti schránek; útočník načítá snímek nejvýše čtyř posledních záznamů a jejich celkový počet. Poštovní a správcovské API používá TCP/443 s předem připraveným modelem TLS; jeho handshake, přihlášení ani skutečné SMTP/IMAP a relay mezi poštovními doménami se nerozepisují. Webová návštěva naopak prochází stávajícím DNS a TLS handshake pro příslušnou doménu. Oznámení v koncových aplikacích a správcovských přehledech jsou výukový pohled. Blokování označeného e-mailu je jednoduchá místní ochrana scénáře. Malware, odposlech, DDoS a hádání hesel tato etapa nepřidává.

- Cookies jsou součást lokální simulace v paměti; aplikace nepoužívá skutečné `document.cookie`, úložiště prohlížeče ani externí sledování. Úplné obnovení aplikace vrátí cookie úložiště i serverové tabulky do výchozího stavu. Zavření monitoru či vypnutí modelového zařízení cookies nemaže. Model podporuje jednu host-only cookie navstevnik pro knihovnu a kořenovou cestu, Max-Age, základní pravidla Secure a zákaz přepsání Secure cookie přes HTTP. Doba platnosti se odvozuje od ručně ovládaných společných hodin cookies. HttpOnly/SameSite=Lax jsou zobrazené atributy; webový JavaScript, jeho API, cizí domény a cross-site kontexty se nevykonávají. Cookies třetích stran, partitioning, úplná pravidla Domain/Path, Session/Expires, přihlašování, fingerprinting, další browserová úložiště a právní souhlasy se nemodelují. ID v1, v2… je názorné rozpoznání prohlížeče, ne identita člověka nebo bezpečný přihlašovací token. Výchozí cookie nemá Secure kvůli porovnání HTTP a HTTPS; nejde o doporučení konfigurace skutečného přihlášení.

- Satelit LEO je pro přehlednost zobrazen v jedné pevné poloze. Skutečný pohyb, předávání spojení mezi satelity, další satelity, laserové mezisatelitní spoje, GEO, rádiové frekvence, modulace, kódování, autentizace, počasí, kapacita a reálná latence se nesimulují. Zakrytí výhledu je ruční binární zásah. Tři animační kroky rádiového letu nejsou měřením výkonu nebo tvrzením, že je každý satelit pomalejší než každá pozemní přípojka. Adresy, NAT na chatě a přenosový kanál jsou volby této modelové topologie, nikoli popis konkrétního komerčního systému. Notebook nemluví přímo se satelitem; mezi ním a satelitní anténou zůstává místní síť a router.

- Ethernet, zjednodušené přemostění Wi-Fi a mobilní kanál, pevně připravené IP adresy, masky, výchozí brány a **ARP sousedé**. Zjišťování MAC pomocí ARP, DHCP, VLAN konfigurace a STP se neanimují. ARP příprava nezpůsobuje předvyplnění MAC tabulek switchů.
- Wi-Fi asociace, hesla/WPA, BSSID a úplná pole 802.11 se nesimulují. Detail Wi-Fi rámce ukazuje pouze zdrojovou a cílovou MAC přemosťovaných dat. Výběr sítě je okamžitý, připravená SSID jsou pevná. Nejde o připojování skutečného počítače k síti.
- BTS se vybírá ručně. Rádiové pokrytí, síla signálu, frekvence, SIM, autentizace, tarify, přechod mezi buňkami, GTP tunely a řídicí protokoly LTE/5G se nesimulují. Přípojka BTS je abstraktní uživatelský kanál; nejsou zobrazeny jeho vnější transportní hlavičky. Stejné časové kroky pro různé přístupy nejsou tvrzením o jejich skutečných rychlostech. Rádio zatím sdílí stejný jednoduchý plánovač jako ostatní spoje.
- NAT je zjednodušený stavový překlad TCP/UDP ve třech domácích routerech, routeru doupěte a routeru kavárny s vazbou na konkrétní protějšek. Časové vypršení záznamů, plný stav TCP, port forwarding, hairpin NAT, překlad ICMP, IPv6 a přepočet kontrolních součtů se nemodelují. Tabulka se sama nevyprazdňuje po každé odpovědi. Mobilní data používají v této etapě přímo modelovou veřejnou adresu telefonu; operátorský CGNAT se nesimuluje. NAT není úplnou simulací firewallu.
- VPN je místní výukový model zapouzdření, ověření, směrování a výstupního NAT. Neotevírá skutečné VPN připojení ani nic neodesílá mimo prohlížeč. Klíče, virtuální IP a protějšky jsou připravené; nevykonává skutečný WireGuard handshake, šifrovací algoritmy, obnovování klíčů, keepalive ani ochranu proti opakování starých zpráv. Neprůhledný náhled představuje chráněný záznam a interně se ověřuje jeho shoda a příslušnost k aktivnímu klientovi. Jde o zobrazení principu, ne bezpečnostní implementaci. Místní domácí cíle jsou z tunelu vyjmuté; uživatelské split tunneling a přímé spojení klientů uvnitř VPN se nenastavují. Výpadek tunelu nepovolí automatický přímý přenos. Mediální skupiny dál zhušťují více paketů a VPN i NAT počítají jejich skutečný modelový počet; nejde o jeden obří paket. Čas a režie neposkytují měření skutečné rychlosti VPN.
- HTTPS je výukový model TLS 1.3 pro prohlížeč pravé i podvodné knihovny. Neprovádí skutečné AES, výměnu klíčů, podpisy ani ověření certifikačního řetězce. Chráněné bajty jsou neprůhledná deterministická ilustrace a interní záznam umožňuje modelové dešifrování jen příslušnému konci. Zjednodušený handshake slučuje několik zpráv a nezobrazuje všechny TLS hlavičky, certifikáty, klíče ani jejich skutečné velikosti. Nejde o věrné měření režie či výkonu. Bez obnovení TLS relace se pro každý pokus naváže nové spojení; HTTP/2, HTTP/3/QUIC, ECH, HSTS, HTTPS přesměrování a šifrované DNS se nemodelují. DNS cache je společná pro obě varianty daného zařízení. Instagram, cloud a chatbot nadále používají svůj dřívější zjednodušený pohled na aplikační data.
- TCP navázání/ukončení spojení, ACK, okna, kontrolní součty, znovuodesílání, řízení toku a zahlcení se nesimulují. Paket Připojení k Instagramu názorně zakládá vratný kanál NAT, nepředstavuje celý TCP handshake. Adresa služby a přihlášení jsou připravené; model nepotřebuje pro každou zprávu DNS ani přihlášení. Pevný odstup paketů slouží k názornému zobrazení souběhu a neodvozuje se od TCP okna. Neúplný první přenos skončí chybou a lze ho zopakovat. Neúplné doručení již přijaté zprávy do Matějovy domácnosti se připraví znovu z uchovaného textu.
- Cloudová synchronizace je výukový snímek celé aktuální sady souborů spouštěný ručně. Automatická replikace, load balancing, automatické přepnutí, obousměrný zápis, historie záloh a obnova po smazání se nemodelují. Dostupnost a aktuálnost kopie zná společný model; síťové zjišťování jejího stáří není samostatný protokol. Ikony představují skupiny serverů, které jsou v realitě rozsáhlejší; nejde o přesnou infrastrukturu skutečného Instagramu nebo cloudového poskytovatele.
- Chatbot je výukový model vzdálené aplikace, ne skutečná generativní AI. Každý neprázdný dotaz dostane stejnou pevnou odpověď vytvořenou v serverové události simulace. Tři kroky zpracování jsou názorná prodleva, nikoliv měření výkonu nebo model neuronové sítě. IP serveru je připravená, TLS, streamování tokenů a úplný protokol HTTP se nesimulují. Formulář přijímá text do 4 000 znaků. Historie je v paměti prohlížeče a po obnovení zmizí. Žádný dotaz neopouští prohlížeč; i server je součást lokální simulace.
- Cloud je výukové úložiště uvnitř stejného prohlížeče. Pracuje s modelovými textovými soubory do 1200 znaků a názvem do 70 znaků; nenahrává skutečné soubory z disku ani nic neposílá na externí službu. Soubory, účty a práva se po novém načtení aplikace obnoví do výchozího stavu. Přihlášení i IP cloudového serveru jsou připravené; DNS, hesla, autentizační tokeny, TLS a sdílení veřejným odkazem se zde nesimulují. Zobrazené JSON bajty jsou didaktický pohled na aplikační data. Klientem přijatý seznam není živý pohled na server.
- Obrázek a video používají deterministické modelové binární bajty dané velikosti, nikoliv skutečně zakódovaný JPEG/MP4. Lokální SVG a čtyřsekundové MP4 slouží jako ukázkový náhled; jejich velikost není velikostí modelového přenosu. Vlastní soubory z disku se nenahrávají. Čas je při skupinování zhuštěný, takže délka animace není měřením ani přímým poměrem skutečných dob přenosu. Zachovává se názorný souběh, skutečný počet modelových datových paketů a úplnost bajtů.
- Instagram je lokální výukový model služby a jednoho posledního chatu s fiktivním účtem `@matej`. Žádné zprávy neopouštějí prohlížeč. Přesná infrastruktura a soukromé protokoly skutečného Instagramu se nereprodukují. Port 443 označuje model chráněného spojení; TLS obal a kryptografie se nesimulují. Zobrazené bajty jsou didaktický pohled na aplikační data. Stavy převzetí a doručení ukazují globální stav modelu; samostatně se po síti animuje až potvrzení přečtení. Rozepsaný text, uložená zpráva a nastavení potvrzení přežijí přepínání aplikací, nikoliv nové načtení stránky.
- Přenos tisku je jednosměrný zjednodušený dokument přes TCP/9100. Tiskárna neposílá zpětné potvrzení; switch se proto z tohoto jednosměrného pokusu nenaučí její MAC. Rozdíl mezi neznámou a známou cílovou MAC lze sledovat při požadavku a odpovědi webu/DNS. Vytištění nastane až po doručení dokumentu.
- Aplikační hlavičky HTTP, HTML a tiskového protokolu jsou schematické. Webová odpověď přenáší jediný malý modelový obsah. Segmentaci a přesné bajty výslovně zobrazuje pokus se zprávou přes Instagram a cloudové operace.
- Žádné reálné měření latence, přenosové kapacity ani modelového času. Změna rychlosti přehrávání není změna parametrů sítě. Fiktivní topologie a ilustrační vzdálenosti nejsou mapou skutečného města.

## GitHub Pages bez sestavování

1. Vytvořte repozitář na GitHubu. Nahrajte `index.html`, složky `assets` a `js` do jeho kořene; README a ostatní soubory můžete přidat také. `index.html` nesmí zůstat v další nadbytečné podsložce.
2. V repozitáři otevřete **Settings → Pages**. V části Build and deployment zvolte **Deploy from a branch**, publikační větev (typicky `main`) a složku **/ (root)**. Uložte.
3. Počkejte na dokončení publikování. Projekt otevřete na adrese `https://UZIVATEL.github.io/REPOZITAR/` uvedené v nastavení Pages.
4. Další verze zveřejníte běžným nahráním změněných souborů nebo commitem do stejné větve. Vlastní workflow, balíčky a build nejsou potřeba. Při změně JS/CSS současně zvyšte `v=32` v odpovídajících cestách v `index.html`, aby prohlížeče rychleji načetly novou verzi prostředků.

Všechny cesty jsou relativní (`./assets/…`, `./js/…`), proto aplikace funguje i v podcestě projektových GitHub Pages. Soubor `.nojekyll` ponechá statické soubory bez zpracování Jekyllem.

Postup odpovídá [dokumentaci GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
